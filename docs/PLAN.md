# Windows 屏幕划取翻译工具 — 实施方案

## Context（为什么做、做成什么样）

从零做一个 Windows 桌面常驻工具：托盘图标 + 全局快捷键 → 屏幕变暗框选 → 截图 → OCR → 翻译 →
框旁弹小窗显示译文 → Esc/点别处关闭。解决"选不中文本的地方"（游戏对话、PDF、图片、网页、视频字幕）
的翻译需求。

第一版明确不做：实时叠加翻译、划词取文本、OCR 手动校正、账号系统、自动更新。

**用户已确认的前提（2026-08-28）：**
- 显示器：单屏
- 翻译方向：自动识别源语言 → 中文
- 翻译服务：大模型类（OpenAI 兼容接口，用户自备 key）
- 主要场景：PDF、图片、网页（原始需求也提到游戏，保留兼容但不作为主要验证目标）

**用户明确要求必须处理好的已知坑：**
1. 多显示器 + 各屏缩放不同时，框选位置与实际截图区域必须完全对齐
2. 遮罩要覆盖所有显示器拼成的完整虚拟桌面
3. 译文窗不抢焦点（尤其全屏游戏）
4. 系统 OCR 语言包缺失要能检测并引导安装
5. 单实例，重复启动唤起已有实例

## 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言/运行时 | C# + .NET 9（机器上已装 SDK 9.0.304，直接开工；升 .NET 10 是改一行 TFM 的事） | Win32/WinRT 互操作最顺；WinRT OCR 直接可用 |
| 目标框架 | `net9.0-windows10.0.19041.0` | 这个 TFM 才能直接调 `Windows.Media.Ocr` |
| 主窗口 UI | WPF（设置窗、译文窗） | 圆角/阴影/排版好看，译文窗需要 |
| 框选遮罩 | 独立的 Win32 无边框置顶窗口，GDI 直接按物理像素绘制 | 绕开 WPF 在跨 DPI 屏上的自动缩放 |
| 托盘 | WinForms `NotifyIcon` | 最稳，无替代品 |
| OCR | Windows 内置 `Windows.Media.Ocr` | 免费、离线、快、无 key。接口化，将来可换 |
| 翻译 | OpenAI 兼容 `/chat/completions` 适配器 | 一次实现覆盖 DeepSeek/通义/智谱/OpenAI/各类代理 |
| 发布形态 | self-contained + single-file，约 90MB 单个 exe | 双击即跑，目标机不需装任何运行环境 |
| 配置 | `%APPDATA%\ScreenTranslator\config.json`，key 用 DPAPI(CurrentUser) 加密 | 不内置任何 key；配置文件里看不到明文 |

### 关键实现决策

**1. 冻屏截图法（一次性解决 DPI 对齐 + 全屏遮罩两个坑）**

按下快捷键的瞬间：
1. 用 `BitBlt` 抓取整个虚拟桌面（`SM_XVIRTUALSCREEN/SM_YVIRTUALSCREEN/SM_CXVIRTUALSCREEN/SM_CYVIRTUALSCREEN`，物理像素）
2. 创建一个覆盖整个虚拟桌面矩形的置顶无边框窗口，1:1 绘制这张位图 + 半透明黑遮罩
3. 用户在这张"冻住的画面"上拖框
4. 松手后，直接从原始位图里按窗口内像素坐标裁剪

因为选区坐标和位图坐标是同一套物理像素，**不存在任何 DPI 换算，也就没有对不齐的可能**。
遮罩窗口按虚拟桌面矩形创建，天然覆盖所有屏。进程声明 Per-Monitor-V2 DPI 感知，
遮罩窗口关闭 WinForms/WPF 的自动缩放，全程走物理像素。

**2. 自动识别源语言**

Windows OCR 不做语言自动检测，必须指定引擎。策略：
- 设置里有「源语言」下拉，默认「自动」，并有一组「候选语言」复选框（默认勾英文 + 日文）
- 「自动」= 对每个已装的候选语言引擎各跑一遍，用启发式打分（识别字符数 × 平均置信度 +
  字符集合理性判断，比如出现假名则强烈倾向日文引擎）挑最优结果
- 用户也可手动锁定语言，更快更准
- 翻译端不需要处理：LLM 天然会自动识别语言并译成中文

**3. OCR 语言包缺失的检测与引导**

- 启动时和每次 OCR 前枚举 `OcrEngine.AvailableRecognizerLanguages`
- 缺失时弹明确提示，给两个按钮：
  - 「打开系统设置」→ 启动 `ms-settings:regionlanguage`（无需管理员，家庭版可用）
  - 「一键安装」→ 提权执行 `Add-WindowsCapability -Online -Name "Language.OCR~~~ja-JP~0.0.1.0"`
- 装完重新枚举即可生效，不需重启程序
- 注意：Windows 11 家庭中文版上 `Add-WindowsCapability` 可能失败，必须保证设置界面这条路可用

**4. 译文窗不抢焦点**

`WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` + `ShowActivated=false` +
`SetWindowPos(HWND_TOPMOST, ..., SWP_NOACTIVATE)`。窗口显示后不调用任何 `Activate()`/`Focus()`。

**5. 单实例**

命名 Mutex（`Local\ScreenTranslator`）+ 命名管道。第二个实例把命令（`show-settings`）
发给第一个实例后自行退出。

**6. 可换引擎的抽象**

```
IOcrProvider      { Task<OcrResult> RecognizeAsync(Bitmap, string[] langs, CancellationToken) }
ITranslator       { Task<string> TranslateAsync(string text, string targetLang, ...) }
ITranslatorConfig { 每家引擎自己声明需要哪些设置字段 }
```
设置界面根据已注册的实现自动列出下拉项和对应字段。加一家 ≈ 一个新文件。

## 分阶段计划

每个阶段结束都产出一个**能双击运行的 exe**。

### 阶段 0 — 能跑起来的空壳

**做什么**：项目骨架、托盘图标 + 右键菜单（框选翻译 / 设置 / 开机自启 / 退出）、全局快捷键注册、
单实例、设置窗口（字段先摆着，能存能读）、DPAPI 加密存储、日志文件、发布脚本。

**你能验证**：
1. 双击 exe，任务栏右下角出现托盘图标（可能在"隐藏图标"折叠区里，拖出来）
2. **再双击一次 exe** → 不出现第二个图标，而是把设置窗口弹到最前
3. 按 `Ctrl+Alt+Q` → 右下角冒一个"收到快捷键"的气泡（这阶段还不框选）
4. 设置窗里随便改点东西 → 关掉 → 重开程序 → 改动还在
5. `%APPDATA%\ScreenTranslator\config.json` 打开看：**里面没有明文 API key**
6. 勾「开机自启」→ 重启电脑 → 图标自动出现；取消勾选后重启不再出现
7. 托盘右键 → 退出 → 图标消失，任务管理器里无残留进程
8. 快捷键被别的程序占用时，程序给出明确提示（不是静默失败）

### 阶段 1 — 框选 + 截图（几何正确性）

**做什么**：冻屏、全虚拟桌面遮罩、拖框交互（放大镜、实时尺寸数字、Esc/右键取消）、
裁剪后保存到 `%USERPROFILE%\Pictures\ScreenTranslator\` 并自动打开。

**你能验证**（这阶段是坑最集中的，请仔细测）：
1. 按快捷键，整个屏幕立刻变暗并**冻住**（暗层下面的画面是按下瞬间的静态图，不再动）
2. 框选一个边界清晰的东西（比如某个按钮、某段文字），截出的图**正好是那块，不偏不缩不糊**
3. 把系统缩放从 100% 改成 **150% 和 175%** 各测一次上一条 ← **DPI 坑的主要验证手段**
4. 框选一个很小的区域（比如 20×20 像素）不崩溃；框选整个屏幕也正常
5. 拖框过程中屏幕上显示当前尺寸数字
6. 按 Esc 取消 → 遮罩消失、不产生文件、原程序不受影响；点右键同样取消
7. 遮罩出现和消失都很快（<200ms），没有白闪、没有黑屏残留
8. 在 PDF 阅读器、Chrome、图片查看器里各测一次
9. （可选）打开一个窗口化/无边框游戏测一次，看能否截到画面

> **单屏限制说明**：多显示器拼接、跨屏拖框、各屏不同缩放这几条，我会按正确方式实现，
> 但你只有一块屏，**这部分你无法亲手验证**。第 3 条改系统缩放能覆盖 DPI 换算这半个坑。
> 将来你接了第二块屏，直接按上面 2/3 条在副屏和跨屏各测一遍即可。

### 阶段 2 — OCR（先只出原文，不翻译）

**做什么**：接 Windows OCR、语言包检测与安装引导、自动语言判定、结果小窗（先显示识别出的原文）、
小窗定位逻辑（贴框边、靠近屏幕边缘自动翻到另一侧）。

**你能验证**：
1. 框一段 PDF 正文 → 原文识别基本正确
2. 框一段网页文字、一张图片里的文字 → 看识别率
3. 框一段日文 → 自动选用日文引擎，不出乱码；框一段英文 → 自动选英文引擎
4. **把日文 OCR 包卸载掉**（或在一台没装的机器上）→ 弹出明确提示 + 可点的安装引导；
   装完后**不重启程序**再框一次就能用了
5. 框一块纯图片、没有文字的区域 → 提示"没识别到文字"，程序不崩
6. 小窗出现在框旁边，**不遮住被框的原文**；在屏幕最右/最下边缘框选时，小窗自动翻到另一侧
7. 按 Esc 或点别处 → 小窗关闭

### 阶段 3 — 翻译打通（端到端可用）

**做什么**：OpenAI 兼容适配器、设置界面（服务预设下拉 + Base URL + Key + 模型名 + 测试连接）、
译文窗、错误处理、不抢焦点。

**你能验证**：
1. 设置里选「DeepSeek」这类预设 → 地址和模型名自动填好 → 只需粘 key
2. 点「测试连接」：key 正确 → 明确的成功提示；key 写错 → **说人话的错误**
   （"key 无效"/"余额不足"/"连不上服务器"，不是"未知错误"或一串英文异常）
3. 框一段 PDF 英文 → 1~3 秒内出中文译文；等待期间小窗显示"翻译中…"
4. 框一段日文 → 同样出中文
5. **不抢焦点验证**：在 Word/记事本里打字 → 按快捷键框选 → 译文窗弹出后，

6. 拔网线 / 故意填错 key → 小窗显示人话错误，**并且仍然能看到 OCR 出来的原文**
7. 翻译很慢时（>10 秒）能超时并提示，不会永远转圈
8. 再次确认 config.json 里 key 是加密的

4. OCR 认错字时可以点「重新翻译」重试

### 阶段 5 — 看图直翻（多模态引擎）　✅ 已实现

> **实现说明（2026-08-29）**：最终没有引入 `ITranslationPipeline` 这一层抽象。
> 两条路的差别只有「提示词 + user 消息的形状」，其余（流式读取、断线抢救、HTTP 错误映射）
> 完全相同，抽成两个实现反而会把这三块经过验证的代码抄成两份。
> 现在的做法是：`OpenAiCompatibleTranslator` 里一个 `_vision` 开关，
> `App.RunPipelineAsync` 按配置二选一。老路发出去的 JSON 与阶段 4 逐字节相同，
> 已用本地桩比对确认。默认引擎选的是**通义千问 VL**（`qwen-vl-max-latest`）。


> **前置硬规矩（阶段 5、6 共同适用）：现有功能一个都不许动。**
> 阶段 0~4 做出来的东西——框选、OCR、文本翻译、小窗、流式、钉住、历史、配色、拖动拉伸——
> 行为、手感、快捷键全部保持原样。新东西一律以**「设置里多出来的一个选项」**的形式存在，
> **默认关闭**，用户不主动切就跟现在一模一样。任何"顺手重构一下"的冲动都要压住：
> 老路是用户已经验证通过的，它就是回退方案。

**做什么**：加第二条翻译路径——把截图**直接**发给能看图的大模型，跳过 OCR。

```
老路（保留，默认）：截图 → Windows OCR 认字 → 文本发给模型翻译 → 小窗
新路（可选）：      截图 → 图片直接发给多模态模型 → 小窗
```

**为什么是它，而不是随便找第二家翻译 API**：见下面「返工风险」第 1、2 条。它一次性解决两个
已经实测遇到的毛病——OCR 认错字（「你」被拆成两个假名），以及紧接着的语种误判。
模型看着原图翻，中间那个会出错的"认字"环节根本不存在了。

**顺带解决的老问题：一张图里好几种语言。**
现在的做法是三个引擎各认一遍全图、打分、**只留分数最高的那一份**。截一小块时没事，
截全屏就露馅：中文赢了，那英文部分留下的就是"中文引擎眼里的英文"——一堆看着还挺像样的
乱码。比漏掉更糟。多模态没有"选一个引擎"这一步，中日英混排它一眼全看懂。

**怎么改（不动老代码的前提下）**：

- 在 OCR 和翻译**上面**再抽一层「翻译流水线」接口，两个实现：
  - `ClassicPipeline` = 现有的 `IOcrProvider` + `ITranslator`，**代码原样搬过去，不改逻辑**
  - `VisionPipeline` = 图片直接进，译文出来
- `App.xaml.cs` 里的编排改成"问配置要一条流水线，然后跑它"，两条路对小窗完全等价
- 新流水线**必须**照样支持 `IProgress` 流式回调，否则小窗的流式、`_settled` 拦截、
  「可能不完整」黄字这些全部失效
- 两套服务配置（地址 / 模型 / key）**分开存、各自 DPAPI 加密**，来回切不用重填
- 图片发之前要缩一下（长边封顶 + JPEG 压缩）。原图 2560×1600 直接发又慢又贵
- 历史记录里标一下这条是哪条路翻的，方便回头对比
- `--testkey` 要能测新引擎（发一张内置的小测试图，看能不能读出字）

**你能验证**：

1. 什么都不改的情况下，程序跟现在一模一样（**这条最重要**）
2. 设置里下拉切到「看图直翻」，**立即生效，不用重启**
3. 同一块区域用两条路各翻一次，自己对比效果——特别是游戏花体字、彩色背景、竖排日文
4. 截一块中英混排的内容，看新路是不是两种都翻对了，老路是不是果然只对了一种
5. 两个引擎的 key 分开存，切过去切回来都不用重填
6. 把新引擎的 key 删掉再切过去 → 明确提示"没配置"，**不崩，也不影响切回老路**
7. 译文照样是一个字一个字冒出来的；钉住、历史、配色、复制、重译全都照常

**已知代价**（要跟用户讲清楚，不能默默发生）：

- 发图比发文字贵，也慢一点
- **必须联网**。老路至少"认字"是本地干的，新路整条都在云上
- DeepSeek 现在的模型不看图，用新路得另配一家（智谱 / 通义 / Claude / GPT 这类）

### 阶段 6 — 全屏原位覆盖（翻译快照）　✅ 已实现

> **实现说明（2026-08-29）**：按计划走了混合模式，没有偷懒改成「看图直翻整屏」。
> 实测确认了这个设计的价值：OCR 把一段日文读成纯乱码，模型仍然给出了正确译文——
> 因为截图跟着一起发过去了。反过来说，**这条路上 OCR 的框错了就全错**，所以
> `--testsnapshot` 的 blocks 图是排查问题的第一站。
>
> 顺带做出来的诊断命令：`--testsnapshot [--dry]`，跑完整流程但不弹窗不抢输入，
> 输出「分段示意图 + 覆盖效果图 + 报告」。`--dry` 用等长占位文字代替译文，
> 不联网不花钱，改排版时先跑它。


> 同样守阶段 5 那条硬规矩：**现有的框选 → 小窗流程一个字节都不动。**
> 这是一个**新的入口**（新快捷键 / 托盘新菜单项），老快捷键的行为保持原样。

**做什么**：按一下新快捷键 → 冻屏 → 认字并记住每块字**在哪** → 整屏一起翻 →
**在原文位置上直接盖上译文** → Esc 或点一下关掉。像网页翻译那样，不是把字都倒进小窗里。

**它建在阶段 1 已经做好的地基上**：按快捷键那一瞬间整个虚拟桌面已经被冻成一张位图、
上面已经铺好了一层像素级对齐的遮罩窗。"在冻住的画面上原地画字"这个舞台是现成的，
不用新造，**坐标 1:1 那条不变量继续管用**。

**关键的架构约束（这条想岔了会白干一遍）**：

> **原位覆盖需要知道"字在哪"，而阶段 5 的多模态直译恰恰把"字在哪"扔了。**
> 多模态模型返回的是一段文字，你让它报坐标它会编。

所以阶段 6 走**混合模式**，不是阶段 5 的简单延伸：

```
截图 → OCR 只负责给出「每块文字在哪」（位置，不指望它认得准）
     → 图 + OCR 文字一起发给多模态模型（图给它看，文字给它对上号）
     → 模型返回每块的译文 → 按块画回原位
```

这样 OCR 认错字不要紧了（模型看着图会自己纠正），但它的位置信息留下来了。
**"多语言选错引擎"的问题也顺手没了**——不再需要挑一个赢家，三个引擎的框都留着，
认成什么样无所谓，反正只用它的坐标。

**怎么改**：

- `WindowsOcrProvider` 现在只留了文字、把 `line.Words[].BoundingRect` 扔了，**位置要捡回来**
  （用一个新的返回类型，老的 `OcrOutcome` 不动，免得波及阶段 2~4 的所有调用点）
- **行要先合并成段落再翻**。OCR 给的是"行"，但一句话经常跨两三行，逐行翻会翻出一堆断句。
  按行间距 / 左边界 / 字高聚类成段，翻完再按比例分回各行的位置上。
  **这一步是整个功能里最容易做成半吊子的地方**
- 整屏一次性批量翻（编号分段，一个请求），不要一段一个请求
- 画的时候：半透明底衬盖住原文 + 自动缩字号 + 允许向右溢出一点
- 遮罩上加一个「看原图 / 看译文」切换，和「复制全部译文」
- Esc / 点一下 / 再按一次快捷键 关掉

**你能验证**：

1. 老快捷键的行为完全没变（**还是最重要的一条**）
2. 按新快捷键，几秒后整屏的字被译文原地盖住，位置对得上
3. 一段话跨了三行，翻出来是**一句通顺的话**，不是三个断句
4. 按住某个键（或点切换）能看回原图，松开又是译文
5. Esc 关掉后屏幕恢复正常，底下的程序没被影响过
6. 多显示器 / 150% 缩放下位置照样准（沿用 `--selftest` 那条不变量）

**明确将就的四件事**（做之前就说好，不当 bug 报）：

1. **译文和原文不一样长**。英译中会短，中译英会长一截。框就那么大，只能自动缩字号 +
   允许溢出。字特别多的时候会被迫缩得偏小
2. **盖不干净**。白底黑字好办（取周围底色填个方块）；压在图片、渐变、游戏画面上的字，
   填出来的方块会难看。**目标是"看得清"，不是"看不出痕迹"**，统一加半透明底衬
3. **排版还原不了**。表格、分栏、竖排日文只能尽力，不追求像素级还原
4. **它是快照，不是实时**。一滚动 / 一切窗口，这层译文就对不上了，Esc 关掉重来。
   实时叠加（一直抓屏、一直比对变化）是另一个量级的工程，**继续不做**

**风险**：全屏文字多的时候，一次要翻几十段，慢和贵都会比框选明显。做之前先拿真实的
全屏截图估一下段数和耗时，如果太夸张就退一步——只对**框选出来的大区域**做原位覆盖，
不做整屏。

## 最可能返工的地方（按概率排序）

**1. OCR 质量不够 —— 最大变数**
Windows 内置 OCR 对白底黑字的印刷体（正是你的 PDF/网页场景）很好，但对扫描歪斜的 PDF、
彩色/半透明背景、竖排日文、带描边的游戏字体、小字号会明显变差。
如果不行，后手有两条：(a) 换本地 OCR 模型（RapidOCR/PaddleOCR ONNX），识别率高很多，
但程序体积从 ~90MB 涨到 300MB+、首次启动多几秒；(b) 走多模态大模型直译（见下）。
**因此 OCR 从一开始就做成可换接口。阶段 2 结束你就能判断够不够用。**

**2. 「自动识别语言」挑错引擎**
多引擎轮询 + 启发式打分在日英混排、短文本（几个词）上可能挑错。
后手：设置里手动锁定语言；或直接走多模态大模型（它看图就知道是什么语言，这个问题自动消失）。
**这两条加起来，很可能最终方案会演变成「截图直接喂多模态大模型」，OCR 反而成了离线备选。**
所以阶段 5 我把它排进来，而不是随便找第二家翻译 API 凑数。

**3. 译文窗的定位和关闭时机 —— 手感问题，一定会来回调**
小窗贴哪边、多宽、字多了怎么滚动、点哪算"点别处"、鼠标移开算不算关闭、
翻译中能不能拖走……这类没有标准答案，得你用过之后说"这里不顺"再改。预留在阶段 4。

**4. 框选交互：松手即翻译 vs 松手后可调边框**
我先按「松手即翻译」做（快）。如果你发现经常框歪要重来，就得改成「松手后显示可拖动的边框 +
确认按钮」，这会改动阶段 1 的交互代码。

**5. 全屏独占游戏（你当前场景用不到，但原始需求提了）**
`BitBlt` 截"独占全屏"的 DirectX 游戏会得到黑屏；置顶的译文窗也可能被游戏吃掉不显示。
要换成 Windows.Graphics.Capture，且 Win10 部分版本上有个去不掉的黄色捕获边框。
真要支持时可能还得把译文直接画回遮罩层上（翻译完成前遮罩不消失），交互手感会不同。

**6. 全局快捷键被高权限程序吞掉**
如果前台程序以管理员权限运行，普通权限的本工具收不到快捷键，需要工具也以管理员启动。
这是 Windows 的限制，没法绕过，只能加个「以管理员身份启动」的选项。
